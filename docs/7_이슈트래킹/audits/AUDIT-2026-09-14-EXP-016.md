# AUDIT — EXP-016 남편·아내 소득 차이와 가사 분담

- 날짜: 2026-09-14
- 독립 검토자: design_audit
- 상태: **설계·드라이버 및 MDE proxy 수정 검증 통과 — proxy 정정은 기준조건 첫 블록 실행 중, 최종 결과 감사 대기**
- 관련: EXP-016, ISS-011, ISS-028, ISS-003, ISS-014
- 범위: 소득 fixture, `minsim_luna_run.py`, `minsim_income_run.py`, `minsim_income_mde.py`, 사전 MDE 산출물
- LLM/API는 호출하지 않았다. 드라이버 검사는 실제 subprocess를 모형으로 대체하고 임시 디렉터리에 가상 캐시만 생성했다. 개인별 원자료는 출력하지 않았다.

## 1. 착수 전 설계 감사

성별을 고정한 새 동일소득 기준 E와 H10/H30/W10/W30를 동일 1,200명에게 독립 세션으로 제시하는 설계를 검토했다. 기존 성별 미지정 EXP-015를 baseline으로 재사용하지 않는다.

- 차이는 낮은 배우자 대비 높은 배우자가 10%/30% 더 버는 비율이다. fixture는 세후 근로소득과 합산소득 불변을 명시하며, 비율 110:100/130:100과 설명용 소득지분 반올림이 일치한다.
- 모든 조건에서 남편 A·아내 B, 주40시간 및 나머지 전제를 동일하게 유지한다. primary는 인물별 `P50(조건)-P50(E)`이다. 여섯 확률과 U를 보존하며 가사분담률의 평균으로 바꾸지 않는다.
- 동일 인물의 선택지 순서는 모든 조건에서 같다. 조건 순서를 블록마다 섞어 조건과 실행 시점의 혼입을 완화한다.
- 이전 categorical k3 또는 phase0 반복 자료는 이번 Luna k1 확률발화의 검정력을 입증하지 않는다. phase0에 조건쌍이 없어 paired 분산은 구할 수 없다. proxy를 작은 값만 선택하지 않고 모두 기록하며 보수적 SD(delta) 상한1과 구분한다.
- 비교4개, 가족 양측 alpha=.05, 목표 power=.8, n=1,200, k=1의 정규근사 계획 MDE는 9.6398%p다. 목표10%p 충족은 해당 가정의 설계상 판단이며 실제 검정력·국민 추론 보장이 아니다.

## 3. 발견사항

### R1 — 실패 재시도 소진 시 다음 블록 PID 호출 가능 [P2, 해결]

초기 드라이버는 target 미완료 수만 runner의 limit에 전달했다. 어떤 미완료 PID가 두 번 실패하면 runner는 해당 PID를 건너뛰고 다음 블록 인물을 호출할 수 있었다. 부모 에이전트가 Counter로 현재 블록의 누락 PID별 시도 수를 확인하고 2회 이상이면 호출 전에 중단하도록 수정했다. 위 모형 검증에서 실제 subprocess 호출 전 차단을 확인했다.

### R2 — NUKPLT18 proxy의 A/B 범주 의미가 반대 [P2, 해결 — 실행 초기 정정]

초기 MDE 코드는 모든 문항·form에서 `pred==1`을 focal로 사용했다. `data/exp009/kr_items.json`에서 NUKPLT18은 A의1이 '원자력 발전 확대', B의1이 '원자력 발전 축소'다. 따라서 기존 SD .32974를 같은 의미의 paired 차분으로 해석하면 안 된다. '확대'를 focal로 고정하면 A는1, B는3으로 정렬해야 한다. 부모 에이전트에게 의미 정렬 후 proxy 및 EXP 기록을 다시 계산하도록 전달했다. 보수적 SD상한1에 따른 MDE9.6398%p와 목표10%p 판정에는 영향을 주지 않는다.

## 4. 현재 판정

실행 fixture와 정상 드라이버 경로는 검증을 통과했다. MDE proxy R2의 수정·재계산 확인 후 호출 전 감사를 닫을 수 있다. 전체 생성·paired 집계·최종 보고서 검증은 실행 완료 후 별도로 필요하다. 모델 정확도나 인간 소득효과를 검증했다는 판단은 하지 않는다.

## 5. R2 후속 수정 검증과 시점 기록

부모 에이전트는 첫 E 조건 64명 블록이 실행되는 시점에 추가 지적을 받아, 소득효과 결과를 분석하기 전에 proxy 정정을 적용했다고 보고했다. 따라서 **모든 감사가 첫 모델 호출 전에 완료됐다고 기록하면 안 된다**. fixture·실행 드라이버의 사전 검증과 MDE proxy 정정 완료 시점을 구분한다. 이 감사에서는 실제 소득조건 생성 결과를 읽거나 집계하지 않았다.

- 소스에서 NUKPLT18 A는1, B는3으로 같은 '확대' 응답 범주를 사용하도록 수정한 것을 확인했다.
- 기존 EXP-009 FULL 300명의 각 form 3회 응답을 독립 재계산했다. `SD(delta)=0.03322166356108445`, 평균 within variance `0.0016666666666666666`로 수정된 mde_plan과 일치한다.
- 이전 미정렬 계획은 `mde_plan_unaligned_superseded.json`으로 보존됐다. 이전/수정 계획의 모든 상한 MDE 값이 동일함을 확인했다.
- 주계획은 처음부터 SD상한1을 사용했다. 표본수·primary·비교4개·목표10%p·전체 상한MDE9.6398%p·생성 설정은 바뀌지 않았다. proxy 수정은 새로운 Luna 응답을 근거로 한 선택이 아니다.

R2는 해소됐고 현재 설계·드라이버·MDE 계산에서 미해결 오류는 발견하지 못했다. 실제 전체 완료와 paired 집계·최종 보고서의 검증은 남아 있다.

## 6. 집계 코드 합성 검증 — 실제 비교 결과 열람 전

`민심테스트/scripts/minsim_income_report.py`를 AST로 추출하고 임시 디렉터리의 가상 인물 1,200명×5조건 입력으로 실행했다. 조건마다 행 순서를 다르게 섞어 같은 행 위치가 아닌 PID로 짝짓는지도 검사했다. 실제 소득조건 raw·비교 결과는 읽지 않았다. 아래 값은 집계 코드 테스트용이며 실험 결과가 아니다.

| 검사 | 증거 | 판정 |
|---|---|---|
| 네 가지 primary 차분 | 합성 P50 평균 E=.6/H10=.5/H30=.4/W10=.7/W30=.8에서 E 대비 -.1/-.2/+.1/+.2 확인; P25는 반대 차분 확인 | 통과 |
| 30%−10% 보조 차분 | H=-.1, W=+.1 확인 | 통과 |
| 여섯 키와 집단 분모 | 모든 그룹에 여섯 확률·차분 보존; 전체1,200, 연도·성별·연령 각 구분의 분모합1,200 | 통과 |
| 미완료 보고 차단 | W30가1,199명인 입력은 AssertionError, summary/보고서 미생성 | 통과 |

## 7. 서버 용량 중단 후 사용자 요청에 따른 재개 감사

김재원의 명시적 재개 요청에 따라 서버 과부하로 응답이 생성되지 않은 요청의 제한적 재시도 개정을 검토했다. 부모 에이전트는 이전 생성 작업이 모두 종료됐으며, 재개 시 단일 누락 요청으로 먼저 확인하고 driver와 동시에 실행하지 않는다고 확인했다.

변경 범위는 income 문항에 한정한다. 기존 두 시도가 모두 serverOverloaded이고 raw/dist가 없으며 유효 응답도 없을 때만 세 번째 시도를 허용한다. 그 밖의 실패는 두 번 상한이며 성공 응답은 재생성하지 않는다. runner와 driver는 동일한 `retry_allowed`를 사용한다. 전체 조건의 기존 raw 행 수와 `--limit` 적용 후 실제 pending 수의 합을 발주 전에 검사해 최대12,000회를 유지한다. 해당 검사는 여러 income 프로세스를 동시에 실행하지 않는 현재 운용 전제에서 검토했다.

| 검사 | 실행 증거 | 판정 |
|---|---|---|
| 제한적 재시도 | 실제 predicate를 AST 추출해 신규·1회·2회 과부하 허용, 3회 소진·타문항·다른 오류·부분 raw·dist 존재·유효 응답 존재 등 총11경계 검사 | 통과 |
| 전역 예산 | 기존11999+예정1 허용,11999+2 거부,12000+0 허용,12000+1 거부 | 통과 |
| 공유 규칙 | driver가 runner의 retry_allowed를 직접 import 및 호출 | 통과 |
| 기존 실험 의미 보존 | 모델·프롬프트·조건·PID·옵션순서·첫 유효 선택·paired 집계 변경 없음; EXP에 실행 전 기술 예외 기록 | 통과 |

이 감사는 실제 요청 없이 순수 함수와 예산 검사 구문을 임시 파일로 검증했다. 단일 회복 확인 요청을 차단할 오류는 발견하지 못했다. 그 요청의 성공 또는 서버 회복을 확인한 것은 아니며, 용량 오류 재발 시 추가 발주를 중단한다. 실제 전체 완료 및 결과 감사는 계속 미완료다.
